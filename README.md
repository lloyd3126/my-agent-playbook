## X

### 串文發布

#### 目的

將較長的內容拆成容易閱讀的 X 串文，而不是全部放在同一則留言中。

#### 發布流程

1. 先回覆目標貼文，發布簡短的開場文字。
2. 回覆自己的開場文字，發布 `[1 / 3]`。
3. 回覆 `[1 / 3]`，發布 `[2 / 3]`。
4. 回覆 `[2 / 3]`，發布 `[3 / 3]`。

#### 檢查點

- 發布第一則前，先讓使用者確認內容。
- 若使用者要求逐則檢查，每發布一則後就暫停。
- 若使用者已確認內容並要求接續完成，可連續發布剩餘內容。

#### 限制

- 不要將多個段落放在同一則留言中。
- 不要加入分隔線。
- 開場文字不需要編號。

### 帳號近期內容整理：通用版

#### 目的

當使用者提供任何 X 帳號時，快速整理該帳號近期公開說了什麼，協助使用者理解內容脈絡；不是模仿對方、替使用者與對方互動，或替對方建立抽象的人格模型。

#### 整理模式

1. **首次整理：建立背景**
   - 回溯近 1 個月可見的原創貼文、引用貼文與回覆。
   - 每一則保留原文短摘錄與直接連結；純轉發預設不納入。
   - 整理主要研究主線、反覆出現的公司、分析方法、時間框架與作者揭露的立場。
2. **日常更新**
   - 預設抓最近 7 天。
   - 包含原創貼文、引用貼文與回覆，掌握最新主題與立場變化。
3. **事件觸發追查**
   - 若近 7 天出現大跌、重大財報、政策變化或主題轉向，回溯事件發生日前 1 個月。
   - 同時整理事件後至今的相關內容，對照作者是否改變、強化或捍衛原有看法。
4. **歷史整理**
   - 由使用者指定長期回溯期間，例如近 3 個月、近 1 年，或從某個日期開始。
   - 整理指定期間內可取得的原創貼文、引用貼文與回覆，依月份或事件建立時間軸。
   - 歸納主要主題、反覆出現的標的、作者立場與重大轉折，並保存每則原文短摘錄與直接連結。
   - 若未指定期間，先確認範圍，不自動假設為近一年。
   - 歷史整理採分批、低頻方式執行，保存每個日期區間的完成、失敗與待續狀態。
5. 預設排除純轉發；若使用者要求，也可以另外整理轉發內容。
6. 不設定固定篇數上限；以指定期間內可取得的公開內容為準。

#### 整理流程

1. 先確認帳號、使用者名稱、整理模式、期間與目前日期。
2. 若已有帳號 Markdown 文件，先閱讀文件前方彙整與下方原始來源紀錄。
3. 依整理模式使用帳號頁面與依帳號篩選的時間軸；首次整理建立背景，後續更新則與既有背景比較。
4. 逐則辨識日期、貼文類型、原文、回覆對象、引用來源與直接連結。
   - 類型判定優先使用 X 的結構化 metadata、貼文卡片、作者／日期區塊與關聯連結，不先用整篇正文搜尋關鍵字。
   - 若作者／日期區塊明確標示「回覆」且有回覆對象，才分類為回覆；若有被引用貼文卡片或引用來源，分類為引用貼文；兩者皆無才分類為原創。
   - 正文或被引用內容中出現「回覆」或「引用」，不能單獨決定貼文類型，避免把引用內容誤判成作者行為。
   - 回覆至少保留回覆對象、作者自己的貼文連結，以及被回覆貼文的原文與連結；若上層內容尚未取得，標記為待補。
   - 若結構化證據不足或訊號互相衝突，標記為「待確認」，不要強制歸類。
5. 完成分類後做一致性檢查：原創、引用貼文、回覆與待確認的數量必須加總等於總筆數；抽查分類邊界與代表性來源後，才寫入帳號文件。
6. 保留每則貼文的原文短摘錄；長文只摘錄足以辨識主旨的部分，完整內容交由連結回查。
7. 將貼文依主題分組，整理整體主線、重複出現的觀點、涉及的公司或人物，以及作者明確揭露的立場或持倉。
8. 區分作者原話、引用他人的說法、Agent 的摘要與 Agent 的推論。
9. 對未驗證的新聞、政策草案、財測或市場傳聞明確標示，不把作者說法當成已確認事實。

#### 請求速度與限流預防

- 這些是防守性的操作預設，不是 X 公開保證的固定限制；目標是在錯誤發生前降低請求密度。
- X 研究一律使用單一瀏覽分頁與單線流程，不平行執行多個搜尋、不同時捲動多個帳號，也不重複開啟相同 URL。
- 初次開啟帳號頁後，先等待約 5 秒確認內容載入；每次捲動後等待約 3–5 秒，確認有新內容後才繼續。
- 切換搜尋區間至少間隔 20–30 秒；重新載入相同查詢至少間隔 60 秒。
- 每完成約 10–15 次捲動，就先保存來源與進度，再進入短暫冷卻，不連續追求一次讀完全部內容。
- 日期區間採自適應切分：先嘗試一個月；若結果過多或載入不穩定，再拆成半月，必要時才拆成 7 天，避免一開始產生過多查詢。
- 已成功完成的日期區間不重新查詢；每次從最後一個成功區間繼續，避免重抓整年。
- 「X 發生錯誤」、「搜尋被限流」與「沒有結果」必須分開記錄，不能把錯誤當成零篇。
- 發生搜尋錯誤時，先冷卻約 2–5 分鐘，原查詢最多重試一次；再次失敗就標記為待重試，不立即增加查詢密度。
- 若連續兩個不同區間都失敗，暫停整體搜尋，改用帳號時間軸或下一個工作階段再補查。
- 每個區間都記錄日期範圍、使用方法、狀態、數量、最後成功日期與待續位置。
- 只有所有指定區間都成功取得、去重並核對後，才能稱為「完整重建」；否則只能稱為「部分重建」或「目前可取得結果」。

#### 輸出格式

1. 先列出整理期間、帳號、搜尋範圍與內容數量。
2. 用一段話說明近期最重要的主線。
3. 以主題整理主要脈絡與作者立場。
4. 提供逐則來源清單，每則至少包含：
   - 日期與類型：原創、引用貼文、回覆或待確認
   - 原文短摘錄
   - 中文摘要
   - 相關公司、股票代號、人物或事件
   - 直接貼文連結
5. 最後列出觀點變化、待確認資訊、可能遺漏與閱讀限制。

#### 文件維護方式

- README 只記錄整理規則；每個 X 帳號另建 `x/accounts/<帳號>.md` 保存資料。
- 帳號文件前方放可快速閱讀的彙整，文件下方放追加式的原文與連結紀錄。
- 每次更新先同步修正前方彙整，再將新增來源追加到文件最下方。
- 不刪除既有來源；若發現錯誤，保留原紀錄並註明修正原因。
- 每筆來源至少包含日期、類型、原文短摘錄與直接連結。
- 若為回覆，另外保留回覆對象、被回覆貼文原文與被回覆貼文連結；若尚未取得，明確標記待補。

#### 互動方式

- 這是一套可持續更新的互動流程，不是只產出一次性的成果報告。
- 每次整理前，先讀取該帳號的 Markdown 文件；若尚未建立，就先建立帳號文件與背景。
- 依需求選擇首次整理、日常更新或事件觸發追查，不重複做不必要的長期回溯。
- 使用者要求歷史整理時，先確認回溯期間；未指定期間時先詢問，不直接抓取一年。
- 完成整理後，先更新帳號文件前方的彙整，再將新增的原文與連結追加到文件下方。
- 只讀取與整理，不按讚、不追蹤、不收藏、不轉發、不回覆、不發布貼文。
- 不要求使用者提供密碼；需要登入時沿用現有瀏覽器工作階段。
- 不把帳號內容改寫成對方口吻，也不主動替使用者與該帳號互動。
- 使用者只要求了解近期內容時，不延伸成投資建議、人物評價或互動策略。
- 若 X 搜尋可能遺漏、內容被刪除、帳號受限、貼文被截斷或只能看到翻譯，必須在結果中明確說明。
- 對金融、政治與產業內容，清楚區分「作者主張」與「已獨立驗證的事實」。

## 財報狗

### 產業報告研究

#### 研究目的

透過財報狗的產業報告、公司頁面與產業鏈資料，建立有來源、可追溯的產業理解。

#### 研究流程

1. 先確認研究主題、產業與時間範圍。
2. 優先閱讀指定期間內最新的產業報告。
3. 延伸閱讀相關報告，例如 HDD、NAND、DRAM 與設備。
4. 將內容分成：
   - 報告中的客觀事實
   - 財報狗的分析判斷
   - Agent 根據資料做出的推論
5. 對照產業鏈、公司名稱、股票代號與上下游關係。
6. 用繁體中文整理核心結論、驅動因素、風險與相關公司。
7. 附上報告連結，讓使用者可以回頭查閱。

#### 互動方式

- 使用者問題明確時，直接開始查找，不重複詢問已知資訊。
- 研究過程中先蒐集多份資料，再形成結論。
- 不把 Agent 的推論說成財報狗原文。
- 若報告內容不足，明確標示不確定性。
- 涉及投資判斷時，區分產業分析與個人投資建議。
- 使用者只要求查看時，不改變收藏、追蹤或其他帳戶狀態。
- 需要登入時，沿用現有瀏覽器工作階段，不要求使用者提供密碼。
